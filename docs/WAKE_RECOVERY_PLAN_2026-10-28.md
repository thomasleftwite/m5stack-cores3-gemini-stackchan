# ウェイク登録・検出・会話開始の復旧計画

版: R2 / 作成・更新: 2026-10-28 / 状態: S07比較の集計・時刻照合完了、実装・実機受入は進行中。

目的は「利用者が登録した呼びかけが、再起動後も同じ登録として検出され、合図後に質問録音と会話を開始すること」。ホスト合成試験、保存整合性、実声検出、会話の成功は別々に判定する。

対象は M5Stack CoreS3 Lite、ESP32-S3、Arduino / PlatformIO `espressif32@6.5.0`、16 MiB flash / 8 MiB PSRAM。実機用正本は `firmware/`。依存は `firmware/platformio.ini` の固定版（M5Unified 0.1.17、M5GFX 0.2.32、ArduinoJson 7.4.3、WiFiManager 2.0.17、esp32-camera 2.0.4）と案件内SimpleVox/ESP-DSP。配布同期は `tools/sync_firmware_sources.mjs`。書込みは既存の `tools/flash_r13_ui_app.py` による app0=0x10000 のアプリのみとし、通常uploadや保存域初期化に置き換えない。

## 原因仮説と反証可能な確認

1. **使っている登録が意図した登録と異なる。** S07はgen2だけが250未満の一致1件、gen1は9候補すべて不一致だった。「旧登録だけが有効」という説明は今回支持されず、現登録を保持して通常会話開始を優先する。CRCはデータの整合性を示すが利用者の意図や作成履歴を示さず、gen2の由来は未解決のまま。
2. **登録とReadyの背景・切出し条件差が実声を変えている。** 同じ候補登録で、通常Ready経路の確認だけ失敗し、背景/長さ/切出しの数値が登録時と系統的に違えば支持される。`EnrollmentWindow`自体は共用済みなので、まず採音時系列と背景取得時点を確認する。
3. **処理中の入力連続性が崩れる。** 連番欠落/キュー枯渇が実測され、不一致区間と対応すれば支持される。呼出し間隔だけでは不十分。必要なら採音フレーム連番と欠落数だけを追加し、音声は外へ出さない。
4. **登録代表例の選択・特徴生成が意図と違う。** 収録ごとのsamples/期待特徴数、選定take、候補/公開/再読込のslot・generation・frames・内部一致を一連で確認する。S06で現RAM破損は支持されていない。

会話開始を止めている診断holdはコード上の確定事項として別に修正する。実声不一致の原因説明に混ぜない。単発の失敗から閾値を緩めず、250を維持して比較する。

## 登録の構造改善案

### 状態と公開の契約

`Idle → Collecting(1..3) → CandidateReady → Verifying → Verified → Publishing → Active`を明示する。取消・失敗は未公開候補だけを破棄し、現登録を継続する。3回の収録は現行の「1秒背景→合図→5秒録音」を維持する。

3回の全組合せ一致は候補生成の成功とする。その後の「呼びかけ確認」は追加登録回ではなく、通常待機と同じ連続入力・背景処理・切出し・閾値で候補が実際に使えるかを確認する工程。確認中は質問録音/送信を開始しない。制限時間・取消・マイク異常・再起動で未確認候補が公開されないことを保証する。

担当間のAPI案は次のとおり。戻り値2の意味が現行から変わるため、main・試験・観測ラベルを同時更新し、「2だから保存成功」という旧解釈を残さない。

| API | 契約 |
|---|---|
| `beginEnrollment()` | 明示セッション開始。前候補・確認成功flag・検出窓を破棄。active/diskは保持 |
| `submitEnrollment(pcm,count)` | 開始済みCollectingのみ受理。1/2回目は1、3回目相互一致は2=候補準備。保存せず代表indexを固定。候補準備後の追加submitを拒否 |
| `candidateReady()` | 3回一致の候補が現セッションに存在することだけを示す |
| `verifyEnrollmentWindow(frame320)` | 通常`detectWindow`と同じprivate入力・切出し・特徴・DTW処理を、固定候補に適用。active登録がなくても動作。実際に一致した同じ候補の確認flagを立てる |
| `commitEnrollment()` | 同じセッション・候補の確認flagがあるときだけ既存公開処理を一度呼ぶ。成功後は候補と確認flagを消し、二度保存できなくする |
| `cancelEnrollment()` | 候補・確認flag・セッション・確認窓を破棄。現active/diskは変更しない |

通常用と候補用の処理は、対象featureを引数にする共通private処理へ寄せる。通常の`registered_`条件を共通処理の入口へ置くと、初回登録が確認不能になるため、通常側だけで検査する。診断用previous比較やmatchedカウンタが候補確認から通常wake開始へ漏れないよう、目的も引数または分離結果で表す。保存の世代・slot選択は公開時点のactiveに対して行う。

次の不変条件はAPI内部で守る。

- 登録開始なし、候補未検証、検証した候補と異なる取引、公開後の再呼出しでは保存できない。
- セッション中に作った候補だけを公開できる。単調な一時session番号と状態で古いUIイベントを拒否する。割込み/非同期化する場合は所有者も一つに限定する。
- 候補検証は現登録の判定を流用せず、候補自身に対して行う。検証後も同じ候補を固定し、公開前に別候補へ置き換えない。
- 既存activeは公開成功まで不変。世代は最後に公開された有効データから一度だけ増やし、既存より小さい世代や重複公開を防ぐ。
- 保存前の実検出は起動を保証する最低条件であり、誤検出率の保証ではない。陰性試験は別に必要。
- 一時書込→CRC/読戻し→公開→最終読戻し→RAM採用を検査。公開後の読戻し失敗や電源断で次回起動が何を選ぶかも試験する。単純な「失敗時は旧登録保持」の表示が次回起動でも真になることを確認する。

### 候補確認の入力開始順序

実装担当間の推奨手順は以下。固定時間の6秒間、判定を捨てながら`verifyEnrollmentWindow`へ入力する案は、関数内部の確認成功flagが先に立つため採用しない。

1. 3回目の候補準備成功後、`AudioTask::clearRecording()`、マイクを有効化、既存の校正を開始する。画面は「確認の準備中。まだ話さないでください」。録音ファイル/質問送信は開始しない。
2. Readyと同じ1.2秒のガード中はAudioTaskのframeを読み続けるが、候補verifierへ渡さない。
3. 候補確認の開始時点で検出窓と確認flagが初期状態であることを保証する。50個の有効frameをverifierへ渡して背景1秒を作る。300frame未満では現在の共通検出処理は判定しない。
4. 50frameを読み終えた時点で「同じ呼びかけを1回話してください」と表示し、30秒の期限を開始する。以後も同じverifierへ連続入力する。最初の判定は合計300frame時点、以後125frameごとで、Readyの窓処理と一致する。
5. verifier一致時だけ`commitEnrollment()`へ進む。不一致の各窓は期限までは待つが、自動で登録回数を追加しない。期限・取消・マイク異常は候補を破棄して設定画面へ戻る。元から未登録なら未登録を保持し、「旧登録を保持」とは表示しない。

校正/背景の進捗は成功したreadのframe数を数える。単なる壁時計経過で背景収集済みと扱わない。静音待ちで発話が検出された場合の背景品質表示は将来改善候補だが、今回の閾値を変える根拠にしない。候補確認は初回登録・再登録の両方で同じUIと経路を使う。

現v3の世代番号だけでは作成主体・登録セッション・DSP条件を復元できない。現在のgen2の由来を後付けで確定できるとは主張しない。まず数値イベントをbegin/candidate/verify/publish/loadに揃える。保存形式へ由来メタデータを加える場合は別版と移行設計が必要なため、v3バイト列を無断拡張しない。

### 画面と結果の区別

「3回の声を確認しました」→「保存前に呼びかけを確認します」→「呼びかけを検出し、保存しました」と段階を分ける。失敗は「声の区間なし」「3回不一致」「待機時に検出できない」「保存失敗」を分け、旧登録が使える場合だけ保持を案内する。通常Readyと診断holdを同じ表示にしない。技術的なslot・CRC等は利用者画面へ追加しない。

S07では現gen2だけが一致したため、旧gen1の復旧試行は現段階で選ばない。将来別の証拠から旧登録を試す場合も、両スロットを残すRAM限定試行で会話開始を先に確かめ、永続採用の方法と再起動後選択を別途定める。片方の削除、gen番号の直接書換え、両方への一致を常時許可する変更は診断結果から自動導入しない。

## 検証と受入条件

合成入力は既存`firmware/tests/simplevox_reference.cpp`等で実際の`ReferenceWake`を呼び、APIの戻り値だけでなく公開ファイル・次回読込・Ready検出まで検証する。入力/表示/会話の統合試験は、通常wake成功がCue/Recordingへ進むこと、hold時に進まないことを検査する。ソース文字列の存在検査だけで動作確認としない。

最低限追加する回帰条件:

- 開始前submit、重複publish、取消後publish、検証前publishが保存を変更しない。
- 3回一致でも候補のReady検証不一致なら未公開。失敗・取消・再起動時に現登録を維持。
- 成功候補のframesと公開/再読込framesが一致し、再読込後の同じ合成語を検出。非対象語・既存非発話5条件は不一致。
- 短い書込、rename失敗、公開前後の読戻し失敗、最新CRC破損、全スロット不正を分ける。再起動後の選択も検査。
- 通常wakeの1回の一致で合図と録音開始は1回。Cue/Recording/Busy/Speaking中はwakeを受け付けず、Ready復帰で過去窓を消す。

実機の短期受入は次を初期目標とする。失敗したら無制限に発話を要求せず、その回の数値を分析して次の変更・試験を決める。

| 証拠 | 合格条件 | 状態 |
|---|---|---|
| 保存保護 | app-only読戻し一致、NVS/FFat/bootloader/table/boot selection前後保持 | S06まで記録あり。最終版で再確認が必要 |
| 起動 | 単一起動、fault/resetなし、DSP4条件一致、意図したslot/gen/framesとRAM/disk一致 | S07も単一起動・整合性成功。登録意図/由来は不明。最終版は未実施 |
| 登録一貫性 | 3回候補・実検出確認・保存・読戻しが同一セッションで成功 | 未実施 |
| 実声陽性 | 想定距離20〜30 cmで各1回の呼びかけを3試行、各回1回検出。うち1回は再起動後 | S07で発話報告に時間対応する一致1件。最終版の3試行・再起動後は未実施。統計的精度保証ではない |
| 実声陰性 | 静音30秒、非対象語3回、TV等想定背景60秒で起動0 | 未実施。背景環境全般の保証ではない |
| 会話開始 | 通常版で一致→合図終了→録音開始。無発話なら送信せずReady復帰 | 未実施 |
| 会話完走 | 質問→API成功→回答音声の再生→Ready、続く呼びかけでも開始 | 未実施。boot/転送だけでは代替不可 |
| 異常/再試行 | 取消・マイク失敗・API非成功で自動無限再試行せず、利用者が復帰可能 | 実機未実施 |
| 長時間・電源断 | 保存途中の電源断、長時間の誤検出/メモリ増加、電源条件を別途確認 | 未実施。短期完了から分離して明記 |

観測は既存`tools/observe_r13_fault.py`の数値allowlistを維持する。session/state/take/selected_take/samples/frames/slot/generation/一致bool/距離/所要時間/欠落数など必要な数値だけを許可する。実声PCM、特徴ベクトル、実声の識別用CRC、文字起こし、APIキー、Wi-Fi情報はホストログへ出さない。CRCは端末内検証に使用し、外部には一致・有効のboolを出す。合成入力のCRCと実声情報を混同しない。
