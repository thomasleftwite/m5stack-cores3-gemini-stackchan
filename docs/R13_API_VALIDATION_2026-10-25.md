# R13 API・接続先確認（2026-10-25）

目的: 準備済みのローカルAPIキーでR13のREST契約を確認し、設定を破壊せずCoreS3実機検証へ進めるかを判断する。
対象版: R13（起点7f20f72）。ユーザーは回答生成モデルをgemini-3.8-flashのままとする判断に同意。
API検証とUSB調査は追加承認済み。PC USBのみ、Grove・外部電源なしを利用者が確認。

追加比較（同日）: [無料枠候補と3.8 Live比較](R13_MODEL_COMPARISON_2026-10-25.md)。回答3.5/3.1への置換試験とLiveはPC側で成功。本番モデル維持の初回結果とは区別する。

## 初回結果

| 対象 | 実測結果 | 判定 |
|---|---|---|
| キー認証・モデル一覧 | HTTP 200。選定した3モデルともgenerateContent対応として掲載 | 成功。実際の課金階層・無料枠残量はこの応答では確認できない |
| TTS（固定の日本語試験文） | gemini-3.8-flash-lite-tts、HTTP 200、7.097秒、WAV/24kHz/mono/16bit、2.8秒、140516 bytes | API契約成功。実スピーカー音質は未確認 |
| STT（上記合成音声を16kHzへ変換） | 初回HTTP 503、1回の再試行でHTTP 200、3.189秒、構造化JSON・非空の認識文、試験の数値2と3を認識 | API契約成功。実マイク・一般的な認識精度は未確認 |
| 回答生成 | gemini-3.8-flash、初回HTTP 503（39.171秒）、再試行TimeoutError（45.162秒） | 失敗 |
| 回答生成の単純要求 | 同じgemini-3.8-flashへ短い固定文、HTTP 503（3.838秒） | 失敗。要求の複雑さだけでは説明できない |
| STT→回答→TTS全体 | 回答生成が成立せず、最終TTSは呼び出していない | 未完了。10秒以内目標は未達確認ではなく、正常な全体経路が未測定 |

503はサービス利用不可という実応答であり、API側の一時的な利用可能性が主な仮説。
原因を確定したわけではない。モデル変更、有料枠への切替、クォータ設定変更は行っていない。
ホストHTTP待機上限は45秒。実機コードの15秒タイムアウトとは異なるため、ホスト成功をそのまま実機成功とみなさない。

API生成呼出は計6回: TTS1回、STT2回、通常の回答生成2回、短い回答生成診断1回。
モデル一覧等の読取りは別。自動再試行・モデル巡回は行っていない。

取得WAVは `tools/check_api_wav.cpp` から実際の `firmware/src/ConversationRules.h` を呼んで検証し、受理された。
WAV140516 bytes、PCM開始44、PCM134400 bytes。PCM後方に追加チャンクがあるが、現行のチャンク走査で検証できる。
確認コマンド: `./tools/check_api_wav.ps1 -WaveFile docs/validation/r13-api-20261025-210943/synthetic-question-24k.wav`。
Pythonツールの構文検査、Web型検査、公開成果物とローカルAPIキーの一致0件、配布37ファイルと正本の一致も確認した。

## 認証の経過

初回のローカル設定では401 / UNAUTHENTICATED / ACCOUNT_STATE_INVALID。
利用者へ設定場所を案内した後の確認では200になった。キーの値・指紋・認識本文・API本文は記録していない。
ローカルのキー入りconfig.jsonは変更せず、Git除外・未追跡のまま扱う。

## USBと保存領域

- 最初のCOM7はESP32-D0WDQ6-V3。ESP32-S3ではなかったため書込みを中止し、利用者が接続機器を変更。
- 変更後のCOM10はUSB VID303A/PID1001、ESP32-S3 (QFN56) revision v0.2。機器固有番号は記録していない。
- 0x8000から0xc00バイトの公開パーティション表だけを読取り。フラッシュへの書込みは0回。

| 領域 | オフセット | サイズ |
|---|---|---|
| nvs | 0x9000 | 0x5000 |
| otadata | 0xe000 | 0x2000 |
| app0 | 0x10000 | 0x300000 |
| app1 | 0x310000 | 0x300000 |
| ffat | 0x610000 | 0x9e0000 |
| coredump | 0xff0000 | 0x10000 |

本体はffatラベルを含む構成で、ビルドのdefault_16MB.csvと不一致。
これはパーティション表の確認であり、実際にFATとしてマウント可能か、何のファイルがあるかは調べていない。
現行コードはLittleFSのマウントを要求し、失敗時には自動フォーマットしない。
そのため、現状のイメージを書くだけでは設定を読めず起動待機となる可能性がある。アプリだけでもまだ書いていない。
既存のnvs/ffat領域を保持する互換対応または移行手順を用意してから実機導入を判断する。

## 成果物・再現方法

- ツール: `tools/validate_r13_api.py`（Python標準ライブラリ、追加インストール不要）。
- `python -B tools/validate_r13_api.py --inspect`: モデル掲載状況の読取りだけ。
- `python -B tools/validate_r13_api.py --run`: 固定合成試験音声で最大4回の生成呼出。マイクを使用しない。
- `--run --resume <前回report.json>`: SHA256で出所を確認した合成試験音声を再使用し、TTSによる試験入力の再生成を省く。
- 初回: `docs/validation/r13-api-20261025-210943/report.json`
- 再試行: `docs/validation/r13-api-20261025-211221/report.json`
- 単純要求: 同ディレクトリの`reply-minimal-diagnostic.json`
- WAVは固定試験文だけの合成音声。個人の録音ではない。APIの認識文・生成回答本文は保存しない。
- 本記録とホスト試験ファイルは実機用配布ZIPの外に保持する。
